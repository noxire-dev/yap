## How the run went

- C lost the same way B did. Its peers used yap in 11 of 18 runs: 18 `yap say`, 2 `yap claim`, 2 `yap doing`, 1
  `yap sessions`, 1 `yap release`. They told each other what they were doing, and both still edited `mux.go`,
  which CooperBench builds the conflict into, so 17 of 18 merges conflicted. A claim warns only before
  Edit/Write, not on a Bash `sed` (board #61). Telling each other didn't stop either one from editing the same
  lines. A, D and E pass because one tree, or one merge order, makes the second change land on top of the first.
- A, D and E all fail on the same two pairs, 56[1,5] and 27[3,4], mostly with one feature passing. Those are
  feature-quality misses, not coordination misses.

- One Go library only. This machine has no Docker, so the run covers go-chi's six lite and core pairs. That
  says nothing about Python or Rust repos.
- Every agent loads the user's whole Claude Code setup: 14 plugins and the global CLAUDE.md, about 44k tokens of
  context before the task. A setup with more agents pays that more times. That is the real setup being measured,
  and it favours A, which runs one process.
- The run was stopped once at 52 rows. `yap gate` asks for a yes on the desktop, so every E run put a dialog in
  front of the user. Two E runs died waiting on it, and the rest carry the click delay in their wall-clock. The
  throwaway daemons now run with `YAP_YOLO=1`. Those 10 E rows are kept in `2026-11-21.e-with-dialog.json`, and E
  was run again in full. A crew a person sets up answers this dialog once per project, so it is not counted as an
  intervention.
- A second bench (v2, `docs/bench/brief-v2.md`) ran on the same plan for part of this run. Wall-clock is under
  that contention, and the plan's weekly-usage change can't be split between the two.
- The shared daemon on 4170 restarted once during the dry run, at 21:41:04Z. Session @sessions shipped 07b68d4,
  not the bench. It was not stopped or restarted after the full run started at 21:45.
