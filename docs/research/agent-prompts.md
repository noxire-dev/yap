# How the best autonomous coding systems write their prompts

Date: 2026-10-03.

Question: what concrete, testable instruction patterns do the strongest coding-agent systems put in their system prompts, skills and task formats, and which of them would improve kumi's four prompts (`planPrompt`, `workPrompt`, `reviewPrompt`, `digestPrompt` in `src/crew.ts`)?

How to read it: one section per source, each with short verbatim quotes, the URL actually fetched, and an "applies to" tag (planner / author / reviewer / digest / harness). Sources are grouped by kind, not by the priority list in the brief. The last two sections rank what to adopt and list what to reject. Anything that could not be reached is marked so; nothing below is reconstructed from memory. Quotes were pulled from raw file contents or the live page; where a page moved, the URL that actually answered is the one cited.

What kumi already does, for comparison (`src/crew.ts`): the author is told nobody is watching, to stay in the worktree, to run the project's checks, to stay inside the ticket, and to end with a summary; round N gets the previous findings. The reviewer gets the ticket, the criteria, the diff, a checked-out worktree, and is told to answer each criterion pass/fail citing file:line or a command, to fail what it cannot verify, and to fail scope creep against the nearest criterion; the verdict is schema-enforced JSON. The planner is told to read the code, produce 1 to 8 tickets, imperative titles, bodies with file paths, 2 to 5 diff-verifiable criteria, and deps only when real. The digest is told to report what changed and where, calls made, and what was left, in four to eight sentences.

## 1. niwa.build and TsukumoHQ (WRAI.TH, dokan)

Reached: https://niwa.build, https://niwa.build/llms.txt, https://niwa.build/answers/why-an-agent-never-merges-its-own-change/, https://niwa.build/answers/autonomous-engineering-crew/, https://niwa.build/answers/parallel-coding-agents/. Unreachable: https://niwa.build/answers/ (index, 404). niwa's own prompt text is not public ("niwa itself remains proprietary", llms.txt); what is public is the protocol, the ticket fields, and the records its crew leaves in the open-source repos.

Protocol (https://niwa.build): reviewers "Start from clean context on exact submitted commit", "Check work against acceptance criteria (not general opinion)", "Answer each criterion with pass/fail and reasoning", "Never review their own submissions", "Run tests and validate merged result in scratch worktree". Tickets carry "Goal statement", "Acceptance criteria (AC1, AC2, etc.)", "Definition of done". "Every ticket carries acceptance criteria. When an agent submits, niwa starts a separate reviewer, from a clean context, on the exact commit that was submitted." Applies to: reviewer (kumi already matches this), planner (kumi has no separate "definition of done" field; criteria carry it).

Reviewer framing (https://niwa.build/answers/why-an-agent-never-merges-its-own-change/): "The agent that wrote a change checks its own assumptions, not the ticket. An independent reviewer answers the ticket's named criteria against the exact commit and can send it back." The reviewer "is an agent too, and it will be wrong sometimes", so "you can overrule any verdict from the terminal". Their own numbers: "52% of changes were sent back at least once before merging (227 of 437)". Applies to: reviewer. Why: a 52% send-back rate is the baseline a strict reviewer produces; kumi's four-round cap sits on top of that.

Parallelism (https://niwa.build/answers/parallel-coding-agents/): "Give each agent its own ticket and its own branch, so no two agents edit the same files at the same time." If the merged result breaks, "main stays where it was and the ticket goes back with the log." Applies to: planner (deps and file disjointness are the planner's job), harness (kumi already feeds the gate log back as a finding).

Human role (https://niwa.build/answers/autonomous-engineering-crew/): users "write the tickets and their criteria, and make the calls a ticket didn't make. Tickets that pass the gate merge on their own." "When one keeps failing review, niwa escalates it to you." Applies to: author (a ticket "didn't make" a call: the author makes it and reports it), digest.

Typed tickets (https://raw.githubusercontent.com/TsukumoHQ/WRAI.TH/main/docs/typed-tickets.md): three fields, `goal` ("one-line intent — why this task exists"), `acceptance_criteria` ("JSON array of strings", "individually testable items"), `dod` ("definition of done — the merge bar"). With `require_typed_ticket` on, "acceptance_criteria must contain at least one non-blank entry; empty arrays or whitespace-only items are rejected" and non-conforming Linear issues "are persisted as refused rows (never dispatched)" with "a loud comment" once. Applies to: planner, harness. Why: the ticket schema is enforced at the door, not by prompt; kumi's `addTicket` already falls back to a default criterion rather than refusing, which is the softer choice.

Merge receipts, as actually committed by niwa on WRAI.TH (https://api.github.com/repos/TsukumoHQ/WRAI.TH/commits?per_page=8): every merge carries trailers `Task:`, `Doer:`, `Branch:`, `Round:`, `Approved-by: review-<task id>`, `Root-Cause:`, sometimes `Decision:`, `Criteria: C1, C2, C3, C4, C5`, `Author-agent:`. Example subject: "chore: [relay/W8 D3] a PR merged event on a deploying task changes nothing". Applies to: planner (titles are observable behaviour statements, not verbs), digest/harness (kumi's receipt has Ticket/Rounds/Reviewed-by/Criterion; it lacks a root-cause line).

Submission record, the "Q&A gate" (https://raw.githubusercontent.com/TsukumoHQ/WRAI.TH/main/features/0776e1a0-bce3-47b0-8a6e-f89331331db7-r2.md): sections "1. Product Brief / Acceptance Criteria", "2. Root cause & decisions" with the author's `ROOT_CAUSE:`, `DECISION:`, `REJECTED ALTERNATIVE:` and a line "Verified exactly as CI runs it: `go test -tags fts5 -race -count=1 ./...` (635 passed, zero race reports)", then the reviewer block:

```
## review-wraith verdict: SHIP
Scope: internal/relay/linear_webhook_test.go (test-only synchronization fix, no logic change), internal/db/db.go (1-line unrelated errcheck fix)
Gate: build -tags fts5 OK / vet OK / gofmt OK / test -tags fts5 -race OK (635 passed, zero races) / golangci-lint v2.12.2 OK (0 issues)
BLOCKERS (must fix before merge):
- none
NITS (non-blocking):
- none
```

then "3. Files changed" (diffstat), "4. QA Log", "5. Timeline", footer "Auto-assembled by the niwa scribe from the Q&A gate." Applies to: author (the report shape: root cause, decision, rejected alternative, exact verify command with its output), reviewer (scope line, gate line, blockers vs nits), digest (the scribe assembles from these parts; it does not re-read the whole diff). Note that the records sampled were all "untyped ticket — no acceptance criteria", so the per-criterion verdict was not observable in them; the commit trailers show typed ones exist.

Review skills (https://raw.githubusercontent.com/TsukumoHQ/WRAI.TH/main/.claude/skills/review-agent-runtime/SKILL.md and .../review-ai-skills/SKILL.md): domain checklists with a fixed verdict block: "review-agent-runtime: PASS | PASS-WITH-NITS | BLOCK / Scope: <files/areas> / BLOCKERS: <none, or file:line — invariant broken + silent harm + fix> / NITS: <non-blocking>". The review-ai-skills gate treats agent-facing docs as code: "the doc is a prompt with consequences", "Autonomous-loop guidance has escape paths and backpressure". Applies to: reviewer. Why: a blocker is file:line plus the invariant broken plus the harm plus the fix; that is the shape of an actionable fail reason.

Relay skill (https://raw.githubusercontent.com/TsukumoHQ/WRAI.TH/main/skill/relay.md): "NEVER ask the user. Send questions to `reports_to` manager instead." "If blocked → block_task with reason → GOTO 1 (pick up another)". "NEVER output 'waiting for input' — NEVER stop after one task". Applies to: author (the no-human rule, with a named sink for questions). Why: kumi has no manager agent; the sink is the finish report and the escalation path.

dokan (https://raw.githubusercontent.com/TsukumoHQ/dokan/main/README.md): "Nonzero exits represent deterministic verdicts, not retry triggers." Applies to: harness (kumi's gate already treats a nonzero exit as a finding, not a retry).

Not found anywhere public: the planner's prompt, the reviewer's prompt, how niwa phrases criteria to the reviewer, the round-2 instruction. Treat the WRAI.TH records as the closest primary evidence.

## 2. Anthropic: Building effective agents

Reached: https://www.anthropic.com/engineering/building-effective-agents.

"Workflows are systems where LLMs and tools are orchestrated through predefined code paths. Agents, on the other hand, are systems where LLMs dynamically direct their own processes." "We recommend finding the simplest solution possible, and only increasing complexity when needed." Applies to: all. kumi is a workflow with an agent inside each step; keep it that way.

Evaluator-optimizer: "particularly effective when we have clear evaluation criteria, and when iterative refinement provides measurable value. The two signs of good fit are, first, that LLM responses can be demonstrably improved when a human articulates their feedback; and second, that the LLM can provide such feedback." Applies to: planner, reviewer. Why: the author/reviewer loop only pays off when the planner wrote criteria the reviewer can articulate a fail against.

"For complex tasks with multiple considerations, LLMs generally perform better when each consideration is handled by a separate LLM call." Applies to: reviewer. kumi's per-criterion rows already approximate this.

"During execution, it's crucial for the agents to gain 'ground truth' from the environment at each step (such as tool call results or code execution)." "It's also common to include stopping conditions (such as a maximum number of iterations) to maintain control." Applies to: author, reviewer.

Tool appendix: "Give the model enough tokens to 'think' before it writes itself into a corner." "Make sure there's no formatting 'overhead'." "Poka-yoke your tools ... we changed the tool to always require absolute filepaths." "Think of this as writing a great docstring for a junior developer on your team." Applies to: reviewer (reason before verdict in the schema), planner (the ticket is the docstring).

## 3. Anthropic: Claude Code best practices

Reached: https://www.anthropic.com/engineering/claude-code-best-practices redirects to https://code.claude.com/docs/en/best-practices (current, rewritten). The April-2025 original via https://web.archive.org/web/20250602202220/https://www.anthropic.com/engineering/claude-code-best-practices.

Current page:

"Give Claude a check it can run: tests, a build, a screenshot to compare. It's the difference between a session you watch and one you walk away from." "Without a check it can run, 'looks done' is the only signal available." Applies to: planner, author.

"Have Claude show evidence rather than asserting success: the test output, the command it ran and what it returned ... it works for sessions you weren't watching." Applies to: author, reviewer, digest. Why: kumi's author ends with "a short summary of what you changed"; it is never asked for evidence.

"a verification subagent ... has a fresh model try to refute the result, so the agent doing the work isn't the one grading it." Applies to: reviewer (frame as refutation).

Adversarial review prompt: "Check that every requirement is implemented, the listed edge cases have tests, and nothing outside the task's scope changed. Report gaps, not style preferences." And the calibration: "A reviewer prompted to find gaps will usually report some, even when the work is sound ... Tell the reviewer to flag only gaps that affect correctness or the stated requirements, and treat the rest as optional." Applies to: reviewer. Why: kumi's reviewer has no calibration line; a gap-hunting reviewer invents fails.

"The most useful specs are self-contained: they name the files and interfaces involved, state what is out of scope, and end with an end-to-end verification step that proves the feature works." Applies to: planner. This is the one-line ticket definition.

Prompt examples: "write a validateEmail function. example test cases: user@example.com is true, invalid is false, user@.com is false. run the tests after implementing" and "the build fails with this error: [paste error]. fix it and verify the build succeeds. address the root cause, don't suppress the error". Applies to: planner (criteria as input/output pairs plus the verify command).

CLAUDE.md hygiene: "For each line, ask: 'Would removing this cause Claude to make mistakes?' If not, cut it." "If you emphasize many lines, none of them stands out." Applies to: all.

"The trust-then-verify gap ... If you can't verify it, don't ship it." "After two failed corrections, /clear and write a better initial prompt incorporating what you learned." Applies to: author, harness (kumi's round N resumes the branch with a fresh session, which matches).

Headless: `claude -p "Migrate $file ... Return OK or FAIL." --allowedTools "Edit,Bash(git commit *)"`; "The --allowedTools flag restricts what Claude can do, which matters when you're running unattended." Applies to: harness.

Wayback original: TDD sequence "Ask Claude to write tests based on expected input/output pairs. Be explicit about the fact that you're doing test-driven development so that it avoids creating mock implementations"; "Tell Claude to run the tests and confirm they fail"; "Ask Claude to write code that passes the tests, instructing it not to modify the tests"; "ask it to verify with independent subagents that the implementation isn't overfitting to the tests". "Have one Claude write code while another reviews or tests it." Applies to: author, reviewer (check that tests were not edited to pass).

## 4. Anthropic: context engineering and writing tools for agents

Reached: https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents and https://www.anthropic.com/engineering/writing-tools-for-agents.

Context engineering: "the smallest possible set of high-signal tokens that maximize the likelihood of some desired outcome." "The right altitude is the Goldilocks zone between ... hardcoding complex, brittle logic in their prompts ... [and] vague, high-level guidance that fails to give the LLM concrete signals." "teams will often stuff a laundry list of edge cases into a prompt ... We do not recommend this. Instead, we recommend working to curate a set of diverse, canonical examples." "agents built with the 'just in time' approach maintain lightweight identifiers (file paths, stored queries, web links, etc.)". Sub-agents return "only a condensed, distilled summary of its work (often 1,000-2,000 tokens)". Compaction keeps "architectural decisions, unresolved bugs, and implementation details while discarding redundant tool outputs". Applies to: all (one example ticket beats five rules), planner (cite paths, don't paste code), author (report size target), digest (the keep/discard rule).

Writing tools: strong task "Customer ID 9182 reported that they were charged three times ... Find all relevant log entries and determine if any other customers were affected" vs weak "Search the payment logs for purchase_complete and customer_id=9182." "Avoid overly strict verifiers that reject correct responses due to spurious differences like formatting, punctuation, or valid alternative phrasings." "try to avoid overspecifying or overfitting to strategies." "instructing agents to output not just structured response blocks (for verification), but also reasoning and feedback blocks ... before tool call and response blocks may increase LLMs' effective intelligence". "what agents omit in their feedback and responses can often be more important than what they include." Error responses should "clearly communicate specific and actionable improvements, rather than opaque error codes". Applies to: planner (outcome plus why, not a mechanical step; don't fix the implementation path), reviewer (reason before verdict; don't fail on cosmetics; read the diff and output, not the author's prose; a fail reason is an error message for the next author run).

## 5. Claude Code docs: memory, skills, headless, subagents

Reached: https://code.claude.com/docs/en/memory, https://code.claude.com/docs/en/skills, https://platform.claude.com/docs/en/agents-and-tools/agent-skills/best-practices, https://code.claude.com/docs/en/headless, https://code.claude.com/docs/en/sub-agents (the docs.claude.com URLs redirect there).

Memory: "Claude treats them as context, not enforced configuration. To block an action regardless of what Claude decides, use a PreToolUse hook instead." "Write instructions that are concrete enough to verify: 'Run npm test before committing' instead of 'Test your changes'." "if two instructions contradict each other, Claude may pick one arbitrarily." Applies to: author (hard limits belong in allowedTools/hooks, not prose), planner (criteria pass the same test).

Skills: "disallowed-tools — Tools removed from Claude's available pool while this skill is active. Use for autonomous skills that should never call certain tools, such as AskUserQuestion for a background loop." "State what to do rather than narrating how or why". Applies to: harness.

Skills best practices: "Default assumption: Claude is already very smart. Only add context Claude doesn't already have." "Match the level of specificity to the task's fragility": low freedom when "A specific sequence must be followed", e.g. "Run exactly this script ... Do not modify the command or add additional flags." Evaluation structure: `"expected_behavior": ["Successfully reads the PDF file ...", "Extracts text content from all pages ...", "Saves the extracted text to a file named output.txt"]`. "Provide a default (with escape hatch)". "Make validation scripts verbose with specific error messages". Applies to: author (the verify command is low-freedom, the implementation is high-freedom), planner (criteria shape), harness.

Headless: "Pass --permission-prompts none when nobody is available to answer permission prompts"; "Claude is told that nobody can approve the request and not to retry it, and the run continues"; "Claude Code removes the tools that need an answer from a person, such as AskUserQuestion, so Claude can't call them." "--bare is the recommended mode for scripted and SDK calls"; without it "a -p session runs the hooks in a project's .claude/settings.json and connects the servers in its .mcp.json, even in a folder you've never trusted." "use --output-format json with --json-schema"; the typo-linter example pipes `git diff main | claude -p "... for each typo in this diff, report filename:line on one line and the issue on the next. return nothing else."` and "Piping the diff means Claude doesn't need Bash permission to read it". Exit code "0 on success and a non-zero code when the run fails". Applies to: harness. Why: `--permission-prompts none` is the canonical way to make the model know there is no human; kumi says it in prose only.

Subagents: "Subagents receive only this system prompt plus basic environment details like the working directory, not the Claude Code system prompt." Example reviewer: "Provide specific line references and suggested fixes." `tools: Read, Grep, Glob, Bash`, `disallowedTools: Write, Edit`. "--append-subagent-system-prompt to append your text to the end of every subagent's system prompt". Applies to: reviewer (read-only plus Bash for tests), author (propagate "no human" to any subagents it spawns).

## 6. agentskills.io and anthropics/skills

Reached: https://agentskills.io/specification, https://raw.githubusercontent.com/anthropics/skills/main/README.md, https://raw.githubusercontent.com/anthropics/skills/main/skills/skill-creator/SKILL.md, https://raw.githubusercontent.com/anthropics/skills/main/skills/skill-creator/agents/grader.md.

Spec: description "Max 1024 characters ... Describes what the skill does and when to use it", poor example "Helps with PDFs."; "Keep your main SKILL.md under 500 lines"; "Keep file references one level deep"; `allowed-tools: Bash(git:*) Bash(jq:*) Read`. Applies to: kumi's own `skills/kumi` skill, harness.

skill-creator: "Prefer using the imperative form in instructions." "Try to explain to the model why things are important in lieu of heavy-handed musty MUSTs." "If you find yourself writing ALWAYS or NEVER in all caps, or using super rigid structures, that's a yellow flag." "Keep the prompt lean. Remove things that aren't pulling their weight. Make sure to read the transcripts, not just the final outputs". "Good assertions are objectively verifiable and have descriptive names". Subagent brief shape: "Skill path / Task / Input files / Save outputs to / Outputs to save". Applies to: all (how to rewrite the prompts), planner (assertion = criterion).

grader.md, the closest Anthropic artefact to kumi's reviewer: "You have two jobs: grade the outputs, and critique the evals themselves. A passing grade on a weak assertion is worse than useless." "Read/examine each file relevant to the expectations ... don't rely solely on what the transcript says the executor produced." "PASS: Clear evidence the expectation is true AND the evidence reflects genuine task completion, not just surface-level compliance; FAIL: No evidence, or evidence contradicts the expectation, or the evidence is superficial (e.g., correct filename but empty/wrong content)". "Cite the evidence: Quote the specific text or describe what you found". "Extract claims from the transcript and outputs ... Flag unverifiable claims". "When uncertain: The burden of proof to pass is on the expectation." "No partial credit: Each expectation is pass or fail, not partial". "Keep the bar high. The goal is to flag things the eval author would say 'good catch' about, not to nitpick every assertion." Output `{"text": ..., "passed": true, "evidence": "Found in transcript Step 3: ..."}` plus `"user_notes_summary": {"uncertainties": [...], "needs_review": [...], "workarounds": [...]}`. "If {outputs_dir}/user_notes.md exists: Read it and note any uncertainties or issues flagged by the executor". Applies to: reviewer (burden of proof, no partial credit, superficial evidence is a fail, nitpicks are not), author (a notes channel for uncertainties and workarounds that the reviewer and digest read), digest.

## 7. Anthropic: Claude prompting best practices (Claude 4.x through current)

Reached: https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices (the claude-4-best-practices URL redirects here; some Claude-4-era wording is gone).

"Golden rule: Show your prompt to a colleague with minimal context on the task and ask them to follow it. If they'd be confused, Claude will be too." Applies to: planner.

"Providing context or motivation behind your instructions ... Claude is smart enough to generalize from the explanation." "Tell Claude what to do instead of what not to do." "Where you might have said 'CRITICAL: You MUST use this tool when...', you can use more normal prompting like 'Use this tool when...'." Applies to: all.

"By default, implement changes rather than only suggesting them. If the user's intent is unclear, infer the most useful likely action and proceed, using tools to discover any missing details instead of guessing." "choose an approach and commit to it. Avoid revisiting decisions unless you encounter new information that directly contradicts your reasoning." "Never use placeholders or guess missing parameters in tool calls." Applies to: author.

Long-running: "Call pwd; you can only read and write files in this directory." "do not stop tasks early due to token budget concerns ... save your current progress and state to memory". "Use git for state tracking". "It is unacceptable to remove or edit tests because this could lead to missing or buggy functionality." "If you create any temporary new files, scripts, or helper files for iteration, clean up these files by removing them at the end of the task." Applies to: author.

Over-engineering block: "Only make changes that are directly requested or clearly necessary ... A bug fix doesn't need surrounding code cleaned up ... Don't add docstrings, comments, or type annotations to code you didn't change ... Don't add error handling, fallbacks, or validation for scenarios that can't happen ... Don't create helpers, utilities, or abstractions for one-time operations." Applies to: author, reviewer (each clause is a checkable fail).

Anti-hardcoding: "Implement a solution that works correctly for all valid inputs, not just the test cases." "Tests are there to verify correctness, not to define the solution." "If the task is unreasonable or infeasible, or if any of the tests are incorrect, please inform me rather than working around them." Applies to: author (a sanctioned "the ticket is wrong" exit), reviewer (test-shaped code is a fail).

Safety: "for actions that are hard to reverse, affect shared systems, or could be destructive, ask the user before proceeding." "don't bypass safety checks (e.g. --no-verify) or discard unfamiliar files". Applies to: author (headless variant: stop and report, do not ask).

"Never speculate about code you have not opened. If the user references a specific file, you MUST read the file before answering." Applies to: reviewer, planner.

"The most common chaining pattern is self-correction: generate a draft → have Claude review it against criteria → have Claude refine based on the review." Applies to: all (kumi's architecture, blessed).

## 8. OpenAI Codex: system prompt, AGENTS.md, review rubric, plan template

Reached: https://raw.githubusercontent.com/openai/codex/main/codex-rs/core/gpt_5_2_prompt.md (full prompt), https://raw.githubusercontent.com/openai/codex/main/codex-rs/core/gpt-5.2-codex_prompt.md (short variant), https://raw.githubusercontent.com/openai/codex/rust-v0.50.0/codex-rs/core/prompt.md (older full prompt incl. `never` mode), https://raw.githubusercontent.com/openai/codex/main/codex-rs/prompts/templates/permissions/approval_policy/never.md, https://raw.githubusercontent.com/openai/codex/main/codex-rs/prompts/templates/review/rubric.md, https://raw.githubusercontent.com/openai/codex/main/codex-rs/collaboration-mode-templates/templates/plan.md, https://raw.githubusercontent.com/openai/codex/rust-v0.50.0/AGENTS.md, https://agents.md. Unreachable on main: `codex-rs/core/prompt.md` and root `AGENTS.md` (removed; tag rust-v0.50.0 used), `codex-rs/core/review_prompt.md` (moved to the rubric path). `docs/getting-started.md` is a redirect stub.

Autonomy (gpt_5_2_prompt.md): "Persist until the task is fully handled end-to-end within the current turn whenever feasible: do not stop at analysis or partial fixes; carry changes through implementation, verification, and a clear explanation of outcomes". "Only terminate your turn when you are sure that the problem is solved ... Do NOT guess or make up an answer." Applies to: author.

Scope: "Fix the problem at the root cause rather than applying surface-level patches." "Do not attempt to fix unrelated bugs or broken tests. It is not your responsibility to fix them. (You may mention them to the user in your final message though.)" "make sure you do exactly what the user asks with surgical precision. Treat the surrounding codebase with respect, and don't overstep (i.e. changing filenames or variables unnecessarily)." "NEVER revert existing changes you did not make unless explicitly requested". "While you are working, you might notice unexpected changes that you didn't make. If this happens, STOP IMMEDIATELY". Applies to: author, reviewer (unrequested renames fail), digest (the "mention them" channel).

Testing: "start as specific as possible to the code you changed ..., then make your way to broader tests as you build confidence. If there's no test for the code you changed, and if the adjacent patterns in the codebases show that there's a logical place for you to add a test, you may do so. However, do not add tests to codebases with no tests." "If there are issues you can iterate up to 3 times to get formatting right, but if you still can't manage it's better to ... call out the formatting in your final message." Applies to: author, planner (test obligation decided from the repo).

No-human mode (rust-v0.50.0 prompt.md, `never`): "you may NEVER ask the user for approval to run commands. Instead, you must always persist and work around constraints to solve the task ... You MUST do your utmost best to finish the task and validate your work before yielding ... Even if you don't see local patterns for testing, you may add tests and scripts to validate your work. Just remove them before yielding." never.md: "Approval policy is currently never ... commands will be rejected." Applies to: author. Why: it names the mode, says requests will be rejected, and grants throwaway validation with a cleanup obligation.

Plans: "Do not make single-step plans." "The content of your plan should not involve doing anything that you aren't capable of doing (i.e. don't try to test things that you can't test)." Low-quality plan "1. Add dark mode toggle 2. Save preference 3. Make styles look good" vs high-quality "1. Define CSS variables for colors 2. Add toggle with localStorage state 3. Refactor components to use variables 4. Verify all views for readability". Applies to: planner.

Final message: "Brevity is very important as a default ... no more than 10 lines". "Lead with a quick explanation of the change, and then give more details on the context covering where and why a change was made. Do not start this explanation with 'summary', just jump right in." "Don't dump large files you've written; reference paths only." File references: "src/app.ts:42", "Do not provide range of lines." Applies to: digest, reviewer (citation format).

Review mindset (gpt-5.2-codex_prompt.md): "prioritise identifying bugs, risks, behavioural regressions, and missing tests. Findings must be the primary focus ... Present findings first (ordered by severity with file/line references), follow with open questions or assumptions, and offer a change-summary only as a secondary detail. If no findings are discovered, state that explicitly and mention any residual risks or testing gaps." Applies to: reviewer.

Review rubric (rubric.md), what counts as a bug: "The bug is discrete and actionable (i.e. not a general issue with the codebase or a combination of multiple issues)." "Fixing the bug does not demand a level of rigor that is not present in the rest of the codebase". "The bug was introduced in the commit (pre-existing bugs should not be flagged)." "The bug does not rely on unstated assumptions about the codebase or author's intent." "It is not enough to speculate that a change may disrupt another part of the codebase, to be considered a bug, one must identify the other parts of the code that are provably affected." "The bug is clearly not just an intentional change by the original author." "Automate when possible: Structure questions to allow for automated grading". "Choose the fastest, most reliable, most scalable method: 1. Code-based grading ... 3. LLM-based grading". "Have detailed, clear rubrics: 'The answer should always mention 'Acme Inc.' in the first sentence. If it does not, the answer is automatically graded as 'incorrect.''" "instruct the LLM to output only 'correct' or 'incorrect'". "Encourage reasoning: Use a grader model with thinking on, so that it reasons before it produces an evaluation score." Grader prompt: "Grade this answer based on the rubric: <rubric>{rubric}</rubric> <answer>{answer}</answer> Output 'correct' or 'incorrect' in <result> tags." Applies to: planner (a criterion states its own fail condition; prefer a runnable check to reviewer judgment), reviewer (binary, reason first).

## 16. SWE-bench Verified

Reached: https://huggingface.co/datasets/princeton-nlp/SWE-bench_Verified/raw/main/README.md, https://cdn.openai.com/introducing-swe-bench-verified/swe-b-annotation-instructions.pdf, https://openai.com/index/introducing-swe-bench-verified/ (403 to WebFetch, reachable with a browser UA), https://raw.githubusercontent.com/SWE-bench/SWE-bench/main/docs/guides/datasets.md.

Task shape: "problem_statement: The issue title and body." "FAIL_TO_PASS: ... tests resolved by the PR and tied to the issue resolution." "PASS_TO_PASS: ... tests that should pass before and after the PR application." Applies to: planner. Why: a ticket is (statement, checks that must flip, checks that must not break); kumi's gate is PASS_TO_PASS, the criteria are FAIL_TO_PASS.

Annotation gate, verbatim: "Imagine that you are an experienced software engineer who has been instructed to create a PR that successfully resolves the above GitHub issue. You have full access to the codebase ... But you are not able to ask for clarification and would need to work exclusively from this information. Is the issue description well-specified enough for a meaningful attempt at a solution?" Scale: "0: The issue is well-specified and it is clear what is required ... 1: There are some blanks to fill in ... but there is a sensible interpretation ... 2: The issue is vague and there is room for ambiguity ... 3: It is almost impossible to understand". Test validity: "3: The tests are too narrow/broad or they look for something different than what the issue is about." "the most common problems occur when there are subtle discrepancies between the tests and the issue text, such as the tests relying on a new function, variable name, or error message that were introduced in the Gold Patch but is not mentioned or differs from the Issue Description." "the high-level requirements for the solution are clear ('what'), but the specifics about the solution are left to the engineer to figure out ('how')." "Please explain your choice above. Include references to specific filenames, function/class names, or lines of code". Writeup: the scikit-learn-14520 test "explicitly checks that the solution must raise a DeprecationWarning ... although the original problem statement ... does not convey this requirement ... the test also requires the agent to exactly match the deprecation message, which was only arrived at after some discussion in the PR which the agent has no access to." Good example: "the FAIL_TO_PASS tests directly assert that the example given in the problem statement has been resolved." "we conservatively ensemble annotations by taking the highest-severity label". Applies to: planner (the gate sentence is kumi's author exactly; every name, message or signature a criterion checks must appear in the ticket body; criteria assert the example in the statement), reviewer (cite file/function; when in doubt take the worse verdict; a gamed test is a fail).

## 19. Patterns worth adopting in kumi

Ranked by expected impact on merge rate and on what reaches the human. Each entry: source, target prompt, suggested wording.

1. Evidence-shaped finish report from the author. Sources: superpowers verification-before-completion and implementer-prompt; Cline yolo ("Verify by execution, never by assumption"; hedge words mean not verified); Claude Code best practices ("show evidence rather than asserting success"); niwa's Q&A record ("Verified exactly as CI runs it: <command> (635 passed)"). Target: author. Wording: "Finish with, in this order: Status DONE | DONE_WITH_CONCERNS | BLOCKED; every command you ran to verify, with its result (pass count, exit code); what changed, by file; every call you made that the ticket did not make, as `Ruling: what — why — what it costs if wrong`; anything you noticed and left alone. If you would write 'should work' or 'probably', run the check instead." Why first: the summary is the digest's only input and the author's own last chance to notice it has not run anything.

2. Rulings, not stalls, plus an exhaustive stop list. Sources: superpowers subagent-driven-development; Codex `never` mode; Cline yolo; Claude prompting best practices ("inform me rather than working around them"). Target: author. Wording: "Nobody can answer a question. Decide it, record the ruling in your report, keep going. Stop and report BLOCKED only for: an action outside this worktree (push, publish, anything on another branch); something destructive or irreversible; a ticket so wrong that every path is a guess, or a criterion that contradicts the code it names. Say what you tried." Why: kumi says "make reasonable calls" but never says what to do when the call is not reasonable to make; today the author either guesses or stalls.

3. Tickets are the decisions the author cannot make alone: files, interfaces, out-of-scope, the verify command. Sources: superpowers writing-plans; Claude Code best practices ("self-contained: name the files and interfaces involved, state what is out of scope, end with an end-to-end verification step"); Codex plan template ("decision complete"; "record it as an assumption"); Copilot's three-part task. Target: planner. Wording for the body rule: "body: the problem, with a reproducing input or example where there is one; the files to change (exact paths); the names and signatures this ticket must produce or consume, so parallel tickets agree without talking; what is out of scope; the command that proves it and what its output looks like when it passes; any assumption you made where the goal was silent. The engineer cannot ask and sees only this."

4. A criterion carries every name, message and signature it checks, and asserts the example in the ticket. Sources: SWE-bench Verified annotation ("tests relying on a new function, variable name, or error message ... not mentioned ... in the Issue Description" is the top failure); Claude Code memory docs ("concrete enough to verify"); Anthropic define-success (a rubric line states its own fail condition). Target: planner. Wording: "criteria: 2 to 5 lines, each one observable behaviour with the input and the expected result, e.g. `slugify('a--b') returns 'a-b'`. Any function name, error text, flag or path a criterion mentions must also appear in the body. Never 'works', 'handles edge cases', 'is tested'."

5. The planner's final gate sentence. Sources: SWE-bench annotation instructions; Claude prompting golden rule ("Show your prompt to a colleague with minimal context"); Roo architect ("Clear enough that another mode could execute it independently"). Target: planner. Wording: "Before you return, read each ticket as an engineer who has the repo, cannot ask anyone, and sees nothing but this ticket. If they would have to guess what done means, fix the ticket, not the engineer."

6. Reviewer calibration: fail correctness and criteria, label the rest, approve what improves. Sources: Claude Code best practices ("flag only gaps that affect correctness or the stated requirements, and treat the rest as optional"); Codex rubric ("Correct implies that existing code and tests will not break ... Ignore non-blocking issues such as style"); Google ("favor approving a CL once it ... definitely improves"; "Nit:" labels); WRAI.TH verdicts (BLOCKERS vs NITS). Target: reviewer. Wording: "A criterion fails when the behaviour it names is missing, wrong, or you could not make it happen. Style, naming, coverage you would like more of, and anything a linter enforces are not fails; put them in a `nits` field and they do not block. Pre-existing problems the diff did not introduce are not fails." Why: niwa sends back 52%; a reviewer with no calibration line burns kumi's four rounds on polish.

7. A fail reason is an error message for the next author run. Sources: Codex rubric ("explicitly communicate the scenarios, environments, or inputs that are necessary for the bug to arise"); WRAI.TH blocker format ("file:line — invariant broken + silent harm + fix"); writing-tools ("specific and actionable improvements, rather than opaque error codes"). Target: reviewer. Wording: "A fail reason names the file:line or the command and its output, the input that shows the gap, and what would make it pass. 'Could not verify' is a fail: say what you ran or read and what was missing, so the next round can supply it."

8. Burden of proof on the criterion; no partial credit; the diff is the ground truth. Sources: anthropics/skills grader.md ("The burden of proof to pass is on the expectation"; "superficial ... evidence" is a fail); superpowers task-reviewer ("Treat the implementer's report as unverified claims"; "a stated rationale never downgrades a finding"); Aider ("Trust this message as the true contents"). Target: reviewer. Wording: "Pass only on evidence in the diff or in output you produced. A commit message, a comment, or a name that claims the behaviour is not evidence. A test that passes without the change, or that asserts nothing, is not evidence." kumi already has "judge what the code does, not what the author meant"; this adds what counts.

9. Round N re-review: ADDRESSED or NOT ADDRESSED per previous finding. Source: superpowers re-review-prompt ("'Attempted' is not addressed: the specific defect must no longer exist"). Target: reviewer, plus a harness change (pass `t.findings` into `reviewPrompt`). Wording: "This is round N. The previous round failed these: [...]. For each, say ADDRESSED or NOT ADDRESSED with file:line. Then judge every criterion again; a fix that broke something else is a new fail." Why: kumi's reviewer currently re-judges from scratch each round, so a half-fix can slip and findings drift.

10. Scope hygiene the reviewer can check: no unrelated fixes (but report them), no reverts of others' changes, no scratch files, no test edits unless the ticket says so, no stray docs, no new dependencies, no renames the criteria do not need. Sources: Codex ("Do not attempt to fix unrelated bugs ... You may mention them"; "NEVER revert existing changes you did not make"; "don't overstep (i.e. changing filenames or variables unnecessarily)"); SWE-agent pre-submit checklist (remove repro script, revert test files); OpenHands (suffix files, docs files, mocks); Claude prompting over-engineering block; Cline ("only libraries ... confirmed ... in use"). Target: author and reviewer. Wording for the author: "Leave the tree as the ticket plus nothing: no scratch scripts, no docs about the change, no new dependencies, no reformatting of lines you did not need to touch, no edits to tests except to add the ones the ticket calls for. A bug you notice outside the ticket goes in your report, not in the diff." Wording for the reviewer: "Every hunk traces to a criterion. One that does not fails the nearest criterion and names the hunk." kumi has "no drive-by refactors"; this makes it enumerable.

11. The stuck-loop breaker. Sources: Cline yolo ("If repeated fixes fail without new evidence, stop making similar edits"); OpenHands and Roo debug ("reflect on 5-7 different possible sources"); superpowers systematic-debugging ("If ≥ 3: STOP"); Codex ("iterate up to 3 times ... then call it out"). Target: author. Wording: "If the same check has failed three times, stop editing. List the possible causes, test the most likely one with a focused check, and only then change code. If that fails too, report BLOCKED with what you tried."

12. Review the tests as evidence. Sources: Google ("Will the tests actually fail when the code is broken?"); mattpocock tdd (tautological, implementation-coupled); bun ("Your test is NOT VALID if it passes with USE_SYSTEM_BUN=1"; no sleep-polling; no "no panic" tests); SWE-bench ("easily gamed"); airflow ("every test must fail without the PR's change"). Target: reviewer, and the planner where a criterion asks for a test. Wording for the reviewer: "A criterion about behaviour passes on a test only if that test would fail without the change: read the assertion, and run it against the base if in doubt. A test that recomputes its expected value from the code, mocks the thing under test, or waits on a timer is not evidence." Wording for the planner: "If a criterion asks for a test, say which regression it must catch."

13. Reason before verdict in the schema. Sources: writing-tools ("reasoning and feedback blocks ... before ... response blocks"); define-success ("reasons before it produces an evaluation score"); building-effective-agents ("enough tokens to 'think' before it writes itself into a corner"). Target: reviewer schema, harness. Change: order `VERDICT` properties `criterion, reason, pass` and tell the reviewer "write the reason, then the verdict". The harness already pairs rows by position, so nothing else moves.

14. Digest contract: lead with the change, list the rulings, name what was verified, never overstate, end terminal. Sources: Codex ("Lead with a quick explanation of the change ... Do not start this explanation with 'summary'"; "reference paths only"); superpowers ("Rulings I made ... each with what it costs if wrong"); bun ("NEVER overstate"); Roo ("NEVER end ... with a question"); temporal ("What changed? Why? Breaking changes?"); OpenHands finish schema. Target: digest. Wording: "Open with what is now true that was not. Then, by file path, what changed. Then every ruling the authors recorded, in order, with what it costs if wrong. Then what was verified (commands, counts) and what was not. Then anything the crew noticed and left alone. Say nothing you cannot point to in a diff or a report. Do not open with 'Summary' and do not end with an offer." The author's report (pattern 1) is what makes the rulings list possible.

15. Harness: tell the model there is no human in the mode, not only in prose. Sources: Claude Code headless docs (`--permission-prompts none`: "Claude is told that nobody can approve the request and not to retry it"; AskUserQuestion removed); skills docs (`disallowed-tools` for background loops); Codex never.md; best practices (`--allowedTools` "when you're running unattended"). Target: harness (`AgentRunner`). Change: run authors and reviewers with `--permission-prompts none`; give the reviewer a read-only tool set plus Bash; decide `--bare` explicitly (bare loses the repo's CLAUDE.md, which the author probably wants and the reviewer probably does not need).

16. How to rewrite the prompts. Sources: superpowers writing-skills (positive output contract for shape problems; "No nuance clauses"); mattpocock writing-for-agents (delete no-op sentences whole; positive phrasing; single-token states); skill-creator ("explain why ... in lieu of heavy-handed musty MUSTs"); Claude prompting best practices ("Tell Claude what to do instead of what not to do"); context engineering (one canonical example over a list of rules). Target: all. Practical consequence: each kumi prompt gets an output contract (parts, in order), one worked example (a ticket; a verdict row), and loses every sentence the model already obeys by default.

## 20. Patterns we reject and why

- Confidence scores on findings (Claude Code code-reviewer "≥ 80"; Codex `confidence_score`). kumi's unit is a binary criterion with the burden of proof on it; a score invites hedging and the harness would only threshold it anyway. The useful residue is pattern 7: say what was run.
- A third verdict state "cannot verify" (superpowers task-reviewer ⚠️). kumi's rule is to fail what it cannot verify, and that rule is the merge gate. Keeping it binary forces the author to supply evidence next round, which is the behaviour we want. The ⚠️ reasoning survives as the required wording of the fail reason.
- "Drop uncertain findings" applied to criteria. Claude Code's "If you are not certain an issue is real, do not flag it" and Codex's "provably affected" are rules for bug-hunting, where a false positive costs trust. For a stated criterion the cost runs the other way: an unverified pass merges unverified code. Keep both rules, in separate sentences: uncertain bug, no finding; uncertain criterion, fail with what was tried.
- "Avoid specific file paths, they go stale" (mattpocock to-tickets). kumi's planner and author run on the same base commit minutes apart; paths do not go stale, and the context-free author needs them. superpowers' exact paths win. Codex's "no more than 3 paths unless needed" is a fair ceiling.
- Severity ladders P0 to P3 and Critical/Important/Minor (Codex, Claude Code plugin, superpowers). kumi's verdict has no severity axis; a criterion passes or fails and the harness never reads a level. Keep only the blocking/non-blocking split (nits).
- ALL-CAPS MUST and IMPORTANT emphasis (Wayback best practices; Aider's lazy_prompt). Current Anthropic guidance says to dial it back and skill-creator calls it a yellow flag. Explain why instead.
- Roo's "if you don't see the expected output, assume the terminal executed the command successfully". The exact failure the reviewer exists to catch.
- "Do not re-run the suite" for the reviewer (superpowers task-reviewer). kumi's reviewer is allowed to run the project's tests where a criterion is about behaviour, and the gate runs the suite anyway. Adopt only the scoping half: a focused test for a named doubt, not a package-wide run.
- Codex plan template's "2 to 4 mutually exclusive options plus a recommended default". There is nobody to pick. Keep the second half only: proceed with the default and record it as an assumption in the ticket.
- Heartbeat loops and "NEVER stop after one task" (WRAI.TH relay). kumi's loop is the daemon, not the agent; an author that keeps going past its ticket is scope creep.
- Model escalation on late rounds (superpowers "Rounds 4-5 — a more capable model"). Plausible, but it is a harness feature with cost implications, not a prompt change; not in this pass.
- "Add or update tests for the code you change, even if nobody asked" (agents.md example) as a blanket rule. Codex's "do not add tests to codebases with no tests" and Claude's "Don't add ... to code you didn't change" are the better default; the planner says per ticket whether a test is in scope (pattern 12).
- A `user_notes.md` side-channel file in the worktree (grader.md). The author's finish report already reaches the reviewer's log and the digest; a second channel means two places to look. Pattern 1 puts the same content in the report.
- Subagents spawned by the author to review its own work. superpowers forbids it ("never spawn a reviewer to check your work") and kumi's design is that the author never judges its own change. Add the prohibition to the author prompt only if transcripts show it happening.
